## 新发现的架构问题

### 1. **数据库设计问题**

#### 1.1 重复表结构
**问题**: `family_notice`, `family_calendar`, `family_dynamic`, `family_album` 四张表结构几乎完全相同

```sql
-- 这四张表有相同的字段
household_id, creator_id, title, body, event_date, yearly, 
pinned, visibility, file_ids, likes, created_at
```

**影响**:
- 违反 DRY 原则,重复代码
- 增加维护成本(字段变更需要修改4处)
- 查询跨类型内容需要 UNION,性能差

**建议重构**:
```sql
-- 统一内容表
CREATE TABLE family_content (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    household_id BIGINT NOT NULL,
    creator_id BIGINT NOT NULL,
    content_type VARCHAR(16) NOT NULL, -- 'NOTICE', 'CALENDAR', 'DYNAMIC', 'ALBUM'
    title VARCHAR(120) NOT NULL,
    body TEXT,
    event_date DATE,
    yearly BOOLEAN DEFAULT FALSE,
    pinned BOOLEAN DEFAULT FALSE,
    visibility VARCHAR(16) DEFAULT 'FAMILY',
    file_ids VARCHAR(2000),
    likes INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_household_type (household_id, content_type, created_at DESC)
);
```

#### 1.2 文件关联设计问题
**问题**: 使用 `VARCHAR(2000)` 存储 `file_ids`,逗号分隔

**影响**:
- 无法建立外键约束
- 查询"某文件被哪些内容引用"需要全表扫描 LIKE
- 文件删除时无法级联清理
- 违反数据库第一范式

**建议重构**:
```sql
CREATE TABLE content_file_mapping (
    content_id BIGINT NOT NULL,
    file_id VARCHAR(64) NOT NULL,
    sort_order INT DEFAULT 0,
    PRIMARY KEY (content_id, file_id),
    INDEX idx_file_content (file_id)
);
```

#### 1.3 缺少外键约束
**问题**: 所有表的 `household_id`, `creator_id`, `assignee_id` 都没有外键约束

**影响**:
- 数据完整性无保障(可以插入不存在的用户ID)
- 依赖应用层校验,容易出错
- 删除用户/家庭时无法级联处理

**建议**: 
- 家庭场景下用户删除是软删除,可以考虑添加外键
- 或者至少在应用层实现严格的引用完整性检查

### 2. **数据一致性问题**

#### 2.1 冗余字段不一致风险
**问题**: `family_task` 同时存储 `assignee_id` 和 `assignee_name`

```java
// TaskServiceImpl.java:66-67
t.setAssigneeId(i.assigneeId());
t.setAssigneeName(name);
```

**影响**:
- 成员改名后,历史任务显示旧名字
- 冗余数据增加不一致风险
- 占用额外存储空间

**建议**:
- 方案1: 只存 `assignee_id`,查询时 JOIN 获取最新姓名
- 方案2: 如果需要历史快照,增加 `updated_at` 和版本控制
- 方案3: 使用视图或查询时动态关联

#### 2.2 Outbox 事件缺少消费者
**问题**: 多个服务有 `event_outbox` 表,但没有看到事件消费者代码

```sql
-- V3__event_outbox.sql
CREATE TABLE event_outbox (...)
```

**影响**:
- 事件只写不读,Outbox 模式未完成闭环
- 表数据持续增长,无清理机制
- 分布式事务无法真正实现

**建议**:
- 实现定时任务扫描 outbox 并发布到 RabbitMQ
- 实现消费者监听事件并更新其他服务
- 添加事件发布状态和重试机制
- 添加已发布事件的清理策略

### 3. **服务边界问题**

#### 3.1 content-svc 职责过重
**问题**: content-svc 管理 4 种不同类型的内容(任务/公告/日历/动态)

**影响**:
- 单个服务承载过多业务逻辑
- 不同类型内容的生命周期和权限规则可能不同
- 数据库表过多

**当前表数量**:
- family_task
- family_notice  
- family_calendar
- family_dynamic
- family_album
- dynamic_like
- event_outbox

**建议**: 
- 短期: 保持现状,但用单表+类型字段重构
- 长期: 如果任务管理变复杂,可拆分为独立服务

#### 3.2 缺少 BFF 或 API 聚合层
**问题**: 客户端需要调用多个服务获取一个页面的数据

**示例场景**: 查看任务详情页
1. 调用 content-svc 获取任务信息
2. 调用 user-svc 获取负责人信息
3. 调用 file-svc 获取附件信息
4. 多次往返,延迟累加

**建议**:
- 在 Gateway 或新增 BFF 层实现数据聚合
- 返回完整的任务视图对象,减少客户端请求

### 4. **安全性问题**

#### 4.1 缺少接口级权限控制
**问题**: 虽然有 `SessionPrincipal`,但权限检查散落在各处

```java
// TaskServiceImpl.java:108-111
if (!p.admin()
    && !Objects.equals(t.getCreatorId(), p.userId())
    && !Objects.equals(t.getAssigneeId(), p.userId()))
    throw new ResponseStatusException(HttpStatus.FORBIDDEN, "仅创建者或负责人可操作");
```

**影响**:
- 权限逻辑散落在业务代码中
- 难以统一管理和审计
- 容易遗漏权限检查

**建议**:
- 使用 Spring Security 方法级注解
- 或实现自定义权限注解和 AOP 拦截器
- 统一权限规则定义

#### 4.2 缺少 API 限流
**问题**: 未见任何限流配置

**影响**:
- 恶意用户可以暴力请求
- 无法防止 DDoS 攻击
- 资源可能被耗尽

**建议**:
- Gateway 层添加基于 IP 的限流
- 关键接口添加基于用户的限流
- 使用 Redis + Lua 实现滑动窗口限流

### 5. **可观测性问题**

#### 5.1 缺少业务指标监控
**问题**: 虽然有 Prometheus 端点,但缺少业务指标

**缺失指标示例**:
- 任务创建/完成数量
- 成员登录次数
- 文件上传大小统计
- 服务调用成功率

**建议**:
- 使用 Micrometer 记录业务指标
- 关键操作埋点(任务状态变更、文件上传等)
- Grafana 配置业务看板

#### 5.2 日志缺少结构化信息
**问题**: 虽然有 traceId,但业务日志缺少关键字段

**建议增加**:
- householdId (家庭ID)
- userId (操作用户)
- operation (操作类型)
- resource (操作资源)

### 6. **性能问题**

#### 6.1 N+1 查询风险
**问题**: 列表查询后可能触发多次单条查询

```java
// 如果需要加载每个任务的创建者信息
tasks.stream().map(t -> {
    // 每个任务都可能触发一次 user-svc 调用
    getUserById(t.getCreatorId());
})
```

**建议**:
- 批量查询接口
- 返回对象包含必要的关联信息
- 使用数据加载器模式(DataLoader)

#### 6.2 缺少数据库连接池配置
**问题**: 未见 HikariCP 明确配置

**建议添加**:
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

#### 6.3 缺少查询优化
**问题**: 某些查询可能性能不佳

```java
// TaskServiceImpl.java:44
.last("LIMIT 500")
```

**建议**:
- 添加分页支持,而不是固定 LIMIT 500
- 考虑添加游标分页或 seek 分页
- 热数据缓存(最近创建的任务)

### 7. **配置管理问题**

#### 7.1 敏感配置未加密
**问题**: 虽然使用环境变量,但 Nacos 中的配置可能未加密

**建议**:
- 使用 Spring Cloud Config 的加密功能
- 或使用 HashiCorp Vault
- 数据库密码、API密钥必须加密存储

#### 7.2 配置分散
**问题**: 每个服务独立配置,公共配置重复

**建议**:
- Nacos 创建共享配置文件(application-common.yml)
- 各服务引用共享配置
- 减少重复配置

### 8. **测试覆盖问题**

#### 8.1 缺少集成测试
**问题**: 只有单元测试,缺少服务间集成测试

**建议**:
- 使用 TestContainers 启动依赖服务
- 编写端到端测试场景
- CI 中运行集成测试

#### 8.2 缺少契约测试
**问题**: 服务间接口变更可能导致运行时错误

**建议**:
- 使用 Spring Cloud Contract
- 或 Pact 进行消费者驱动的契约测试
- 确保服务接口兼容性

## 优先级建议

### 高优先级 (影响正确性和安全性)
1. ❗ 实现 Outbox 事件消费者和发布机制
2. ❗ 修复 file_ids 的数据库设计(关系表)
3. ❗ 添加 API 限流
4. ❗ 统一权限控制

7. 🔸 实现业务指标监控
8. 🔸 添加批量查询接口

### 低优先级 (优化改进)
9. 🔹 添加外键约束
10. 🔹 配置加密和集中管理
11. 🔹 增加测试覆盖率
12. 🔹 添加 BFF 聚合层

## 总结

架构整体设计合理,但存在以下核心问题:
1. **数据库设计不够规范** (重复表、逗号分隔存储)
2. **分布式事务未完成** (Outbox 只写不读)
3. **缺少保护机制** (限流、熔断部分完成但不全面)
4. **可观测性不足** (缺少业务指标)

对于家庭场景,当前架构可能过度工程化,但如果要保持微服务架构,需要完善上述问题。
