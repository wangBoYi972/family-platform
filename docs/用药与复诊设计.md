# 用药与复诊设计

## 1. 目标与边界

在既有家庭档案能力上补齐两件日常事：记下一种药每天服用的时刻，以及记下复诊日期；到当天打开家庭端或移动端能看到提醒。

边界：

- 不新建服务。全部代码放进 `family-archive-svc`，继续使用该服务的 AES 密钥、`family_archive` 库和家庭隔离。
- 网关不新增路由。新接口统一挂在 `/api/archives` 下，复用已有 `Path=/api/archives/**` 规则。
- 不改动档案面板现有的证件、健康、文档分类行为。
- 不主动弹微信授权。服务端推送只产出可调用的扫描结果，模板没配好时不会发消息。

## 2. 数据与加密

Flyway 迁移文件：`backend/family-archive-svc/src/main/resources/db/migration/V2__health_care.sql`。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `medication_plan` | `encrypted_body`、`dose_times`、`start_date`、`end_date`、`visibility`、`enabled` | 药名、剂量、备注组成 JSON 后用 `ArchiveCipher` 的 AES-GCM 加密，密文存 `encrypted_body`；一天多个时刻按 `HH:mm` 去重排序后存 `dose_times`。 |
| `medication_check` | `household_id`、`plan_id`、`check_date`、`dose_time`、`checked_by` | 唯一键 `(household_id, plan_id, check_date, dose_time)` 保证重复勾选幂等；先查再插，并检查 `DuplicateKeyException` 兜并发。 |
| `follow_up_visit` | `encrypted_body`、`visit_at`、`remind_days`、`visibility` | 标题、医院或科室、备注加密；就诊时间和提前提醒天数保留明文供查询。 |

加密上下文沿用档案服务的 AAD 方式，并加上表前缀区分：`{householdId}:medication:{id}`、`{householdId}:follow_up:{id}`。密钥仍来自 `family.archive.key` / `FAMILY_ARCHIVE_KEY`，不新增配置项。

`householdId` 和 `ownerId` 只从 `SessionPrincipal` 取；请求体里没有也不接受家庭编号。列表接口只返回加密正文还原出来的药名/剂量/备注（或复诊标题/医院/备注）以及必要的时间、可见性字段，不附带任何额外医疗描述。

## 3. 可见性

`PRIVATE` 表示仅本人可读可改，管理员也不例外：

- 查询统一带 `household_id = 会话家庭` 且 `(owner_id = 会话用户 OR visibility = 'FAMILY')`。
- 找不到记录一律返回 404；因此其他成员和管理员读取别人的私有用药/复诊都是 404（不是 403，避免探测存在性）。
- 更新、删除在可读基础上再校验 owner；家庭可见但非本人的记录返回 403。
- 当天待服用列表、未来 30 天复诊列表、提醒扫描都走同一套过滤；扫描结果按记录 owner 收敛，不会把家人的药名带进别人的提醒。

## 4. 接口

全部在 `/api/archives` 下，网关无需改动：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/medications` | 用药计划列表、新建 |
| GET / PUT / DELETE | `/medications/{id}` | 用药计划详情、修改、删除 |
| GET | `/medications/today` | 当天应服用的每一次（含已勾选状态），按家庭时区判断起止日 |
| POST | `/medications/{id}/checks` | 勾选某次已服用；日期由服务端按家庭时区取今天，重复请求不产生第二行 |
| GET / POST | `/follow-ups` | 复诊列表、新建 |
| GET / PUT / DELETE | `/follow-ups/{id}` | 复诊详情、修改、删除 |
| GET | `/follow-ups/upcoming?days=30` | 未来 N 天复诊（1 ≤ N ≤ 30，默认 30） |
| GET | `/reminders/today` | 供订阅消息链路调用的当天提醒扫描结果 |

「今天」由 `FamilyClock` 统一计算，默认 `Asia/Shanghai`（与数据库 `serverTimezone` 一致），可用 `family.timezone` 覆盖。复诊的 `visit_at` 按该时区语义存储，因此跨时区部署时日期不会漂移。

## 5. 提醒

### 打开应用时

`apps/shared/health-schedule.mjs` 与 `anniversary-remind.mjs` 采用同一套做法：纯函数 + 按日期的本地去重 key。

- `todayDoses(plans, { today, checks })` 计算「今天该吃哪几次」：过结束日不再出现，未开始的计划不出现，停用的计划不出现，已勾选的记为已服用。
- `todayFollowUps(visits, today)` 把带时区的时间折算到家庭时区后判断是否今天。
- 家庭端（`apps/mini-family`）和移动端（`apps/mobile-app`）登录后调用 `/medications/today` 与 `/follow-ups/upcoming?days=30`，把未服用的药和今天的复诊合并成一条弹窗；两类提醒各写 `family_health_medication_reminded_{date}`、`family_health_follow_up_reminded_{date}`，同一天不再弹，跨天自然失效。
- 这里不调用 `wx.requestSubscribeMessage`，也不做静默授权。

### 服务端订阅消息

现有订阅消息链路（`OfflineReminderService` + `WxService`）目前只有 task / anniversary 模板位，没有 `medication-reminder` 模板配置。因此本次只提供可调用的扫描方法：

- `HealthCareService.scanTodayReminders(SessionPrincipal, LocalDate)` 返回 `HealthReminderVO` 列表，`templateKey` 固定为 `medication-reminder`，`kind` 区分 `MEDICATION` / `FOLLOW_UP`，`businessId` 形如 `medication:{userId}:{date}`。
- 上游链路补上模板后直接消费这些结果并按 `businessId` 做当日幂等即可；`WxService` 在微信未配置、模板缺失或用户未订阅时返回 `skipped`，不抛错、不消耗配额。

## 6. 前端

只新增一份共享面板：`apps/shared/panels/HealthPanel.vue`。

- 家庭端：`我的家` → `用药复诊`，与 `档案` 并列。
- 移动端：`我的家` 子标签 → `用药复诊`，与 `档案` 并列。
- 面板分「今天的药」和「复诊」两段：可新增/编辑/删除用药计划与复诊，勾选已服用，查看未来 30 天复诊。
- `用药复诊` 与 `档案` 共用同一请求封装；档案面板文件未改动。

## 7. 测试

- `HealthCareIntegrationTest`（H2 + Flyway，使用档案服务同一把 AES 密钥）覆盖：私有计划与复诊对其他成员和管理员 404、健康正文密文入库、过结束日不出现在今天、同一时刻重复勾选只有一行、复诊按家庭时区算今天、提醒扫描不跨家庭。
- `ArchiveIntegrationTest` 补开 `spring.flyway.enabled=true`，让 H2 测试库真正执行 V1/V2 迁移。
- `apps/shared/health-schedule.test.mjs`：`node --test` 覆盖跨日时区、结束日边界、时刻去重、当天复诊过滤、两类提醒的本地去重 key 和文案。

运行：

```bash
mvn -pl family-archive-svc -am test
node --test apps/shared/health-schedule.test.mjs
npm run build:h5 --prefix apps/mini-family
npm run build:h5 --prefix apps/mobile-app
```

## 8. 验收路径

1. 家庭端登录 → `我的家` → `用药复诊` → 记一种药（含两个服用时刻、起止日、可见性）→ 在「今天的药」勾选一次已服用。
2. 同页「复诊」新增一条今天的复诊。
3. 切到 `我的家` → `档案`，原有证件/健康/文档档案仍在，行为不变。
4. 移动端重复上述操作；两端都用同一份面板，数据由同一套接口提供。
