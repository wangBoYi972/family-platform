## 二、核心架构问题

### 🔴 问题1: 服务拆分粒度不合理

#### 1.1 过度拆分的服务

**问题:**
- **family-content-svc** 承载了5种不同的业务实体(任务/动态/相册/日程/公告)
- 这5种实体**业务逻辑互不相关**,只是因为都属于"内容"就放在一起
- 导致该服务职责不清晰,边界模糊

**数据证据:**
```java
// family-content-svc 混合了多种业务实体
controller/
├── EntryController.java    // 处理动态、相册、日程、公告
└── TaskController.java      // 处理任务

model/
├── Task.java               // 任务实体
├── Entry.java              // 动态/相册/日程/公告的统一实体(通过type字段区分)
└── EntryKind.java          // 枚举: DYNAMIC/ALBUM/CALENDAR/NOTICE
```

**问题分析:**
- `Entry` 是一个"上帝对象",通过 `EntryKind` 枚举来区分4种完全不同的业务
- 动态(DYNAMIC)、相册(ALBUM)、日程(CALENDAR)、公告(NOTICE)的业务逻辑完全不同
- 强行用一个实体类表示,违反了**单一职责原则**

#### 1.2 拆分不彻底的问题

**family-user-svc** 混合了多种职责:
- 用户基础信息管理
- 认证鉴权(登录/注册/JWT)
- 家庭成员管理
- 邀请码生成
- 密码重置
- **微信通知推送**(与用户管理无关)

---

### 🔴 问题2: 数据库设计不合理

#### 2.1 共享数据库问题

查看数据库设计:
```sql
-- family-content-svc 的数据库结构
entry (动态/相册/日程/公告统一表)
├── id
├── kind (DYNAMIC/ALBUM/CALENDAR/NOTICE)  # 用一个字段区分4种业务
├── content
├── title
└── ...

task (任务独立表)
├── id
├── title
├── status (TODO/IN_PROGRESS/COMPLETED)
└── ...
```

**问题:**
- **一个表(entry)承载4种业务实体**
- 不同业务的字段混在一起(日程需要时间,动态不需要;相册需要图片,公告不需要)
- 大量 NULL 值,查询效率低
- 违反**数据库范式**

#### 2.2 跨服务数据依赖混乱

```java
// family-content-svc 直接依赖 family-api 调用其他服务
family-content-svc/pom.xml:
  <dependency>
    <groupId>com.familyhome</groupId>
    <artifactId>family-api</artifactId>  // 包含 UserFeignClient、FileFeignClient
  </dependency>
```

**问题:**
- 服务间通过 Feign 直接调用,形成**强耦合**
- 没有使用事件驱动架构,导致服务间同步调用
- 一个服务故障会级联影响其他服务

---

### 🔴 问题3: API 设计不符合 RESTful 规范

#### 3.1 URL 设计混乱

```java
// family-content-svc 的 API
GET  /api/entries?kind=DYNAMIC     // 查询动态
GET  /api/entries?kind=ALBUM       // 查询相册  
GET  /api/entries?kind=CALENDAR    // 查询日程
GET  /api/entries?kind=NOTICE      // 查询公告
POST /api/entries                  // 创建(任意类型)
```

**问题:**
- 4种不同的业务实体用同一个 `/api/entries` 端点
- 通过query参数 `?kind=XX` 区分业务类型,不符合 RESTful 规范
- 应该是独立的资源路径:
  - `/api/dynamics`
  - `/api/albums`
  - `/api/calendars`
  - `/api/notices`

#### 3.2 响应格式不统一

```java
// 部分接口返回统一包装
{
  "code": 0,
  "message": "success",
  "data": { ... }
}

// 部分接口直接返回实体
{
  "id": 1,
  "title": "..."
}
```

### 🔴 问题4: 缺少核心基础设施

#### 4.1 缺少配置中心

**现状:**
- 每个服务有独立的 `application.yml` 和 `application-local.yml`
- 敏感配置(数据库密码、API Key)直接写在配置文件中
- 修改配置需要重启服务

**缺失:**
- ❌ Nacos Config / Spring Cloud Config
- ❌ 配置加密存储
- ❌ 配置动态刷新

#### 4.2 缺少服务治理

**现状:**
- 有 Nacos Discovery(服务注册发现)
- 但缺少:
  - ❌ 熔断降级(Sentinel / Hystrix)
  - ❌ 限流(Sentinel)
  - ❌ 链路追踪(Skywalking / Zipkin)
  - ❌ 服务监控(Prometheus + Grafana)

#### 4.3 缺少统一日志收集

**现状:**
- 每个服务独立输出日志到本地文件
- 排查问题需要登录多台服务器查看日志

**缺失:**
- ❌ ELK / EFK 日志收集
- ❌ 分布式追踪ID(TraceId)
- ❌ 日志聚合分析

### 🔴 问题5: 代码层面问题

#### 5.1 实体类设计问题

```java
// family-content-svc/model/Entry.java
@Data
public class Entry {
    private Long id;
    private EntryKind kind;  // DYNAMIC/ALBUM/CALENDAR/NOTICE
    
    // 以下字段并非所有kind都需要
    private String title;      // 动态不需要title
    private LocalDateTime scheduledAt;  // 只有CALENDAR需要
    private List<String> images;  // 只有ALBUM需要
    private Boolean pinned;    // 只有NOTICE需要
    // ...大量可选字段
}
```

**问题:**
- **贫血模型** - 只有getter/setter,没有业务逻辑
- 大量字段根据 `kind` 决定是否使用,违反**接口隔离原则**
- 应该拆分为独立的领域模型

#### 5.2 Service 层职责不清

```java
// family-content-svc/service/impl/EntryServiceImpl.java
@Service
public class EntryServiceImpl implements EntryService {
    
    @Autowired
    private EntryMapper entryMapper;
    
    @Autowired
    private UserFeignClient userClient;  // 跨服务调用
    
    @Autowired
    private FileFeignClient fileClient;  // 跨服务调用
    
    // Service层直接处理Feign调用,耦合度高
    public EntryVO getEntry(Long id) {
        Entry entry = entryMapper.selectById(id);
        // 调用用户服务获取创建人信息
        MemberApiVO member = userClient.getMember(entry.getCreatorId());
        // 调用文件服务获取图片信息
        List<FileApiVO> files = fileClient.getFiles(entry.getFileIds());
        // 组装VO
        return toVO(entry, member, files);
    }
}
```

**问题:**
- Service 层直接调用 Feign Client,违反分层架构
- 多个服务调用没有容错机制
- 一个服务故障会导致整个接口失败

## 三、重构方案

### 方案A: 微服务重新拆分 (推荐)

#### 3.1 按业务领域拆分

```
family-platform-v2
├── 基础设施层
│   ├── family-gateway          # 统一网关
│   ├── family-config-center    # 配置中心(新增)
│   └── family-common           # 通用组件
│
├── 用户域
│   ├── family-auth-svc         # 认证鉴权服务(拆分)
│   └── family-member-svc       # 成员管理服务(拆分)
│
├── 内容域
│   ├── family-task-svc         # 任务管理服务(独立)
│   ├── family-dynamic-svc      # 动态服务(独立)
│   ├── family-album-svc        # 相册服务(独立)
│   ├── family-calendar-svc     # 日程服务(独立)
│   └── family-notice-svc       # 公告服务(独立)
│
├── 存储域
│   ├── family-file-svc         # 文件服务(保留)
│   └── family-archive-svc      # 档案服务(保留)
│
├── 通信域
│   ├── family-im-svc           # 即时消息(保留)
│   ├── family-media-svc        # 音视频(保留)
│   └── family-notification-svc # 通知推送(新增,拆分自user-svc)
│
└── 智能域
    └── family-ai-svc           # AI助手(保留)
```

**核心改进:**
1. **family-content-svc 拆分为5个独立服务**
2. **family-user-svc 拆分为2个独立服务** (认证 + 成员管理)
3. 新增**通知推送服务**
4. 新增**配置中心服务**

---

### 方案B: 单体架构重构 (成本最低)

如果团队规模小,微服务维护成本高,建议合并为单体架构:

```
family-platform-monolith
├── backend-monolith (单体应用)
│   ├── domain/
│   │   ├── user/        # 用户域
│   │   ├── task/        # 任务域
│   │   ├── dynamic/     # 动态域
│   │   ├── album/       # 相册域
│   │   ├── calendar/    # 日程域
│   │   ├── notice/      # 公告域
│   │   ├── file/        # 文件域
│   │   ├── archive/     # 档案域
│   │   ├── im/          # 消息域
│   │   ├── media/       # 媒体域
│   │   └── ai/          # AI域
│   │
│   ├── infrastructure/  # 基础设施
│   │   ├── security/
│   │   ├── storage/
│   │   └── messaging/
│   │
│   └── application/     # 应用层
│       ├── api/
│       └── events/
│
└── frontend (前端保持不变)
```

**核心改进:**
1. **合并所有微服务为单体应用**
2. 按领域划分模块,每个模块独立
3. 使用本地事件总线代替跨服务调用
4. 降低运维复杂度

## 四、数据库重构方案

### 4.1 拆分 entry 表

**当前:**
```sql
entry (kind: DYNAMIC/ALBUM/CALENDAR/NOTICE)
```

**重构后:**
```sql
dynamic (动态表)
album (相册表)
calendar (日程表)
notice (公告表)
```

### 4.2 引入事件表

```sql
domain_event (领域事件表)
├── id
├── aggregate_type (聚合根类型: TASK/DYNAMIC/...)
├── aggregate_id
├── event_type (事件类型: CREATED/UPDATED/DELETED)
├── event_data (JSON)
└── created_at
```

## 五、技术栈建议

### 5.1 需要引入的组件

| 组件 | 用途 | 优先级 |
|------|------|--------|
| Nacos Config | 配置中心 | 🔴 高 |
| Sentinel | 熔断/限流 | 🔴 高 |
| Skywalking | 链路追踪 | 🟡 中 |
| ELK Stack | 日志收集 | 🟡 中 |
| Prometheus + Grafana | 监控告警 | 🟢 低 |

### 5.2 需要优化的点

1. **API 网关增强** - 添加认证/鉴权/限流/熔断
2. **统一异常处理** - 全局异常拦截器
3. **统一响应格式** - 定义统一的 API 响应结构
4. **引入 MapStruct** - 替代手写实体转换
5. **引入 Caffeine** - 本地缓存,减少跨服务调用

## 六、重构优先级

### 阶段1: 紧急问题修复 (1-2周)

1. ✅ 修复所有 `catch (Exception e)` 违规代码
2. ⏳ 为关键类添加 Javadoc 注释
3. ⏳ 统一 API 响应格式
4. ⏳ 引入全局异常处理

### 阶段2: 架构优化 (1个月)

1. ⏳ 拆分 `family-content-svc` 为独立服务
2. ⏳ 重构 `entry` 表为独立表
3. ⏳ 引入 Nacos Config
4. ⏳ 引入 Sentinel 熔断降级

### 阶段3: 基础设施完善 (1-2个月)

1. ⏳ 引入 ELK 日志收集
2. ⏳ 引入 Skywalking 链路追踪
3. ⏳ 引入 Prometheus + Grafana 监控
4. ⏳ 编写完整的架构文档

## 七、结论

**当前最大问题:**
1. 🔴 `family-content-svc` 职责过重,需要拆分
2. 🔴 `entry` 表设计不合理,一表多用
3. 🔴 缺少配置中心和服务治理组件
4. 🔴 服务间强耦合,缺少容错机制

**建议:**
- 如果**团队规模 >= 5人**,采用**方案A**(微服务重新拆分)
- 如果**团队规模 < 5人**,采用**方案B**(合并为单体架构)
- 优先解决**阶段1紧急问题**,再考虑架构重构
