# 正式环境验收执行方案

日期：2026-11-24。

## 文档目的

本方案把《正式交付执行记录》《正式认证实施方案》《开发验收清单》中列出的 7 项"发布阻断项"逐条拆成可执行、可留证的验收任务。每项包含：当前状态、前置条件、执行步骤、通过标准、证据留存、验收人。任何一项未达到"通过标准"，不得对外发布。

同时纠正一处文档与实现的偏差：`微服务实施规划.md` 写 `family-media-svc` 职责含"独立 SFU"，但当前实现是浏览器端 WebRTC mesh（网状），服务端只做信令与 TURN 凭据下发，**并无 SFU**。8 人以上多人通话能力需按本方案第 4 节的选型结论补齐后，才能宣称达成。

## 总览与优先级

| # | 验收项 | 当前状态 | 阻断级别 | 建议顺序 |
| --- | --- | --- | --- | --- |
| 1 | MySQL 与 Nacos 实例联调 | 配置就绪、未真实联调 | P0 | 1 |
| 2 | 真实短信 / 微信身份认证 | 代码就绪、平台未配置 | P0 | 2 |
| 3 | 对象存储真实环境验收 | S3 适配就绪、未验收 | P0 | 3 |

## 1. MySQL 与 Nacos 实例联调

### 当前状态
`infra/docker-compose.yml` 已编排 Nacos v2.4.2（standalone）、MySQL 8.4、Redis、RabbitMQ，各服务 prod profile 通过 `NACOS_SERVER_ADDR` 与 `jdbc:mysql://mysql:3306/...` 连接，9 个业务库的 Flyway 迁移齐全。但从未真实联调：本机 Docker daemon 未启动，历史全链路测试是 10 个本地 JVM 直连本地 MySQL + Node 轻量代理替代网关。

本轮已修复的阻断缺陷：compose 中有 16 处 `${VAR:default}` 单冒号插值写法（Docker Compose 要求 `${VAR:-default}`），会导致 `docker compose up` 直接报 `invalid interpolation format` 而无法启动。现已全部改正，`docker compose config --quiet` 校验通过。

### 前置条件
- 目标机器已安装 Docker Engine 24+ 与 Compose 插件，daemon 正常运行。
- `infra/.env` 已按 `.env.example` 填好全部必填密钥（JWT ≥32 字节、archive key、Nacos token、9 个库的 root/app 密码）。
- 服务器时间同步（NTP），否则 JWT 到期判断会偏移。

### 执行步骤
1. `cd infra && docker compose config --quiet` —— 确认无插值/语法错误。
2. `docker compose up -d nacos mysql redis rabbitmq`，等 mysql healthcheck 变 healthy。
3. 验证 MySQL：进入 mysql 容器执行 `SHOW DATABASES;`，确认 9 个库齐全（对照 `infra/mysql/init/00-databases.sql`）；抽查任一业务库 `SELECT COUNT(*) FROM flyway_schema_history;`，确认迁移版本已落地。
4. 验证 Nacos：浏览器打开 `http://<host>:8848/nacos`，用 `.env` 的 `NACOS_AUTH_TOKEN` 对应账号登录，确认服务列表能注册进来。
5. `docker compose up -d` 启动全部服务，等所有容器 healthy。
6. Nacos 控制台确认 10 个业务服务（gateway + 9 svc）全部注册为 UP；任一服务下线与重启，观察 Nacos 是否在 30s 内更新实例列表。
7. 跑接口回归：`node scripts/api-smoke.mjs`（指向容器化网关地址），要求全通过。

### 通过标准
- 9 个库存在、Flyway 版本为最新、无 failed 迁移。
- Nacos 控制台 10 个服务实例全部 UP，服务上下线可被正确感知。
- api-smoke 全量通过；跨服务 Feign 调用（如 AI→content、media→user）在容器网络内正常。

### 证据留存
`docker compose ps` 输出、Nacos 服务列表截图、MySQL `SHOW DATABASES` 与 `flyway_schema_history` 查询截图、api-smoke 结果 JSON。

## 2. 真实短信 / 微信身份认证

### 当前状态
登录链路是白名单账号密码认证（BCrypt、失败锁定、会话撤销，测试 11 项通过），并非真实身份平台认证。微信侧 `WxService`/`WxProperties` 实现的是**订阅消息推送**（`enabled=false`，appid/secret/模板 ID 全空），不是微信登录；短信只有开发用固定验证码。`docs/正式认证实施方案.md` 明确写"正式短信和微信身份平台尚未配置"。

### 前置条件
- 微信开放平台/公众号 AppID + AppSecret，配置合法域名与 JS 接口安全域名；小程序侧需完成微信认证。
- 短信服务商账号（阿里云/腾讯云），签名与模板已审核通过。
- 生产密钥注入走密钥管理，不落代码库。

### 执行步骤
1. **微信登录**：确认 `WxController`/`WxService` 的 `code2session` 链路是否完整；如只有订阅消息无登录，先补齐"微信 code 换 openid → 绑定白名单成员 → 签发 JWT"的服务端逻辑。
2. `WxProperties` 填入真实 appid/secret/templates，`enabled=true`，`apiBase` 保持官方地址。
3. 短信：接入真实短信 SDK 替换固定验证码实现，配置 `accessKey/secretKey/signName/templateCode`。
4. 真实验证：用真实手机号收验证码登录；用微信真机授权登录；验证 openid 与成员的绑定关系。
5. 安全回归：重放攻击、码有效期、失败锁定、跨家庭越权（复用 `PasswordAuthenticationIntegrationTest` 思路补真实平台场景）。

### 通过标准
- 真实手机号能收到短信并完成登录；真实微信授权能换取 openid 并绑定成员登录。
- 错误密码/过期验证码/未白名单账号被正确拒绝；失败锁定生效。
- 密钥不在代码与日志中泄露；微信接口调用失败有明确错误提示。

### 证据留存
真机授权截图、短信到达截图、服务端 openid 绑定记录、安全回归测试结果。

## 3. 对象存储真实环境验收

### 当前状态
`S3FileStorage` 已完整实现 S3 兼容协议（MinIO/OSS/COS，路径式访问、显式 endpoint、凭据仅从环境注入），`LocalFileStorage` 为默认。当前 `.env` 的 `FAMILY_FILE_STORAGE_TYPE=local`，S3 endpoint/bucket/密钥全空，从未连真实对象存储。

### 前置条件
- 真实对象存储桶已创建（MinIO 自建或云 OSS/COS），拿到 endpoint、region、bucket、accessKey、secretKey。
- 桶的 CORS 与访问策略配置好（私有读写，下载走后端授权，不公开桶）。

### 执行步骤
1. `.env` 设 `FAMILY_FILE_STORAGE_TYPE=s3`，填 5 个 S3 变量。
2. 重启 file-svc，确认 `@PostConstruct initialize()` 的 `ensureBucket()` 能 headBucket 成功；桶不存在时应能自动创建。
3. 跑文件上传→元数据→下载→删除闭环：`node scripts/api-smoke.mjs` 的 File 组（3 项）。
4. 边界验证：超过大小限制的文件被拒、无权限用户下载他人文件被拒、删除后对象真的从桶里消失（登录对象存储控制台核对）。

### 通过标准
- 上传/下载/删除全链路通过，对象确实落在真实桶中。
- 私有访问边界成立：越权下载被拒；桶无公开读权限。
- 换一台机器重启服务，历史文件仍可下载（证明文件不在本地磁盘）。

## 4. 公网 TURN 实网穿透与压测，以及 8 人以上 SFU

### 当前状态（最大缺口）
coturn 已在 compose 编排（`network_mode: host`、3478 端口、49160–49200 中继段、静态密钥 + `IceServerService` 时效性凭据 HMAC-SHA1）。但：
- compose 第 278 行注释明确公网部署必须填 `--external-ip=<公网IP>`，当前默认 `127.0.0.1`；
- 公网实网穿透与压测从未执行；
- **SFU 完全缺失**：`apps/shared/call/webrtc-mesh.js` 是浏览器端 mesh（每两人一条连接），`FAMILY_MEDIA_MAX_PARTICIPANTS=8` 就是它的容量天花板。8 人以上需要新增 SFU 架构，不是改配置能解决的。

### 4.1 公网 TURN 穿透与压测

**前置条件**
- 公网服务器 + 域名，防火墙放行 UDP/TCP 3478 与 UDP 49160–49200。
- coturn `--external-ip` 配置正确（多网卡/云 NAT 环境尤其重要）。

**执行步骤**
1. coturn 配置填公网 external-ip 与 realm，启动后用 `turnutils_uclient` 做连通性测试：`turnutils_uclient -v -u <user> -w <cred> <公网IP>`，确认 Allocate/Channel 成功。
2. 用内网穿透受限的真实网络（4G/移动网络、对称 NAT）做端对端通话，强制走 relay（浏览器 webrtc-internals 里确认候选类型为 relay）。
3. 压测：用 `scripts/call-browser-smoke.mjs` / `call-browser-group.mjs` 拉起多浏览器实例，逐步加压到目标并发通话数，观察 coturn 的 CPU/带宽/会话数。

**通过标准**
- 对称 NAT / 移动网络下媒体可经 TURN 中继连通，双向音视频正常。
- 目标并发下 coturn 无丢包雪崩，资源占用在预算内。

### 4.2 八人以上 SFU 选型（AB 对比）

| 维度 | 方案 A：mediasoup（自建） | 方案 B：LiveKit（开源自建） | 方案 C：商用（腾讯云 TRTC / 声网） |
| --- | --- | --- | --- |
| 架构 | Node.js + WebRTC，选择性转发，需自研信令对接 | 成熟 Go SFU，自带信令/SDK/录制 | 全托管，SDK 接入 |
| 与现有信令整合 | 复用到现有 `CallSocket` 的房间/参与者模型，自研转发控制，工作量最大 | 用其 SDK 替换前端 `MeshRtc`，服务端用 Token 鉴权，工作量中等 | 前端换 SDK，服务端签名发 Token，工作量最小 |
| 8 人以上能力 | 支持，单 SFU 数十路需调优 | 支持，官方已验证大规模 | 支持，弹性最强 |
| 运维成本 | 高（自己管 worker、CPU 亲和、扩缩容） | 中（单二进制 + Redis） | 低（免运维） |
| 数据合规 | 完全私有 | 完全私有 | 媒体经第三方，家庭隐私数据需评估 |
| 成本 | 服务器成本 | 服务器成本 | 按分钟计费，长期最贵 |
| 适配本项目 | 家庭隐私优先、已有 mesh 信令可演进 | 隐私+成本+工作量平衡最佳 | 合规评估复杂，不推荐 |

**推荐结论**：选 **B（LiveKit 开源自建）**。理由：家庭场景强调隐私与私有部署，排除商用 C；mediasoup 需自研转发控制、工作量与运维成本最高，而 LiveKit 提供完整 SDK 与参与者管理，能最快把 `FAMILY_MEDIA_MAX_PARTICIPANTS` 从 8 提升到 20+。若团队 Node.js 能力强且追求极致可控，可选 A。

**决策已定案（2026-11-24）**：选定 **B. LiveKit 开源自建**。完整改造方案见 `docs/LiveKit-SFU改造方案.md`（含服务端 Token 签发代码、前端双栈改造、录音适配、灰度回滚、20 人压测口径）。下表对比保留作决策依据。

### 4.3 mesh → SFU 改造要点（以 LiveKit 为例）
1. 新增 `family-sfu` 部署单元（compose 加 livekit-server + Redis），配置密钥与对外域名。
2. 服务端新增"加入房间 Token"接口：复用现有通话参与者校验与家庭隔离，签发 LiveKit JWT。
3. 前端 `apps/shared/call/` 用 LiveKit SDK 替换 `MeshRtc`，保留 `CallPanel` 的呼叫/接听/挂断 UI 与 `call-client.js` 信令流程。
4. 录音链路（`call-recorder.mjs`）需适配从 SFU 订阅的远端轨道。
5. 更新 `FAMILY_MEDIA_MAX_PARTICIPANTS` 上限，补 8→20 人的压力测试用例。

### 通过标准
- TURN 在受限网络下中继通话成功；压测达标。
- SFU 模式下 8 人以上（目标 20）多人通话音视频正常、无卡顿；家庭隔离与参与者鉴权成立。
- 文档与代码一致：更新 `微服务实施规划.md` 中 media-svc 的职责描述。

### 证据留存
turnutils 测试输出、webrtc-internals relay 候选截图、压测报告、SFU 多人通话截图、改造后的架构图。

### 当前状态

1. 两个小程序分别用开发者工具"预览"生成二维码，真机扫码安装体验版。

## 6. 监控告警

### 当前状态
Prometheus 抓取配置 + Grafana 面板已就位，但此前没有告警规则与通知渠道。本轮已补齐：
- 新增 `infra/prometheus/alert.rules.yml`（4 组 9 条规则：服务下线/抖动、5xx 错误率、响应延迟、堆内存、GC、服务调用失败、Outbox 发布失败、活跃家庭数）。
- 新增 `infra/prometheus/alertmanager.yml`（Webhook 通知 + 邮件示例 + 告警抑制）。
- Prometheus 接线 `alerting` 与 `rule_files`，补齐此前遗漏的 iot(8092)/ledger(8093) 两个抓取目标。
- compose 新增 alertmanager 服务并挂载配置。

### 前置条件
- 第 1 项容器化联调完成，各服务 `/actuator/prometheus` 可被抓取。
- 通知渠道就绪：企业微信/钉钉群机器人中转网关，或 SMTP 邮件账号。

### 执行步骤
1. 起 alertmanager + prometheus，打开 `:9090/alerts` 确认 9 条规则加载为绿色、`/actuator/prometheus` 目标全部 UP。
2. 配置 `alertmanager.yml` 的 webhook url 指向真实通知网关（或切到邮件 receiver）。
3. 故障注入验证：停掉一个服务实例，确认 `ServiceDown` 在 1m 内触发并收到通知；恢复后确认 resolved 通知。
4. 注入高错误率/高延迟，确认对应规则触发；验证 `inhibit_rules` 抑制告警风暴。

### 通过标准
- 9 条规则全部加载无语法错误；目标全 UP。
- 故障注入能在预期时间内触发并送达通知，恢复后收到 resolved。
- 告警分级（critical/warning/info）与抑制规则生效。

### 证据留存
Prometheus alerts 页面截图、通知送达截图（群消息/邮件）、故障注入与恢复时间记录。

## 7. 备份恢复演练

### 当前状态
`backup-mysql.sh`（Linux）、`backup-mysql.ps1`（Windows）、`restore-mysql.ps1` 已存在，但此前有两个缺陷：备份脚本漏库（Linux 漏 iot/ledger，Windows 漏 ai/iot/ledger，与 9 库实际不符）；且从未做过恢复演练。本轮已补齐：
- 两个备份脚本的库列表改为与 `00-databases.sql` 一致的 9 库。
- 新增 `drill-restore.sh`（Linux）与 `drill-restore.ps1`（Windows）演练脚本：在隔离库 `<db>_drill<时间戳>` 中恢复，逐表比对行数，全程不触碰生产库，自动清理并输出证据报告。
- 给三个 PS1 脚本补 UTF-8 BOM，修复 PowerShell 5.1 下中文乱码问题。

### 前置条件
- 第 1 项 MySQL 实例可用；至少有一份由备份脚本产生的真实备份目录。
- MySQL root 凭据；磁盘空间足够放隔离库。

### 执行步骤
1. 执行一次真实备份：`MYSQL_ROOT_PASSWORD=xxx ./backup-mysql.sh`，得到 `backups/<时间戳>/` 含 9 个 .sql。
2. 执行演练：Linux `MYSQL_ROOT_PASSWORD=xxx ./drill-restore.sh ./backups/<时间戳>/`；Windows `$env:MYSQL_ROOT_PASSWORD="..."; ./drill-restore.ps1 .\backups\<时间戳>`。
3. 演练脚本会自动建隔离库、导入、逐表比对行数、清理，并输出 `drill-report-<时间戳>.txt`。
4. 核对报告结论为 PASS；抽查一张关键业务表（如 `family_user.family_user`）的行数与生产一致。

### 通过标准
- 9 个库全部恢复成功，所有表行数与生产一致（报告 PASS）。
- 演练过程未对生产库造成任何写入；隔离库被正确清理。
- 报告文件留存完整。

### 建议：纳入定期演练
用自动化调度每月跑一次演练（可用项目自动化能力配置），把"备份可用性"从一次性验收变成持续保障。演练报告按时间戳归档。

### 证据留存
