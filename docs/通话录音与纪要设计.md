# 通话录音与 AI 纪要设计

> 2026-11-23。目标：通话结束后自动得到「这通电话说了什么、谁要做什么」，不用边打边记。

## 1. 一句话方案

录音在**客户端**完成（混音后分段），音频存**私有文件服务**，由**媒体服务**编排、**AI 服务**转写并整理，结果落库供全家人查看。

链路：

```
通话中（浏览器/WebView）
  ├─ Web Audio：本地麦克风 + 每个远端流 → 混成一路
  ├─ MediaRecorder：每 3 分钟一段，webm/opus（iOS 为 m4a）
  └─ 挂断
       ├─ 逐段 POST /api/files（visibility=FAMILY，带用户令牌）
       ├─ POST /api/media/calls/{callId}/recording   ← 只登记 fileId、时长、同意标记
       └─ 媒体服务 @Async
            ├─ POST /api/ai/transcribe（fileId）→ qwen3-asr-flash，base64 输入
            ├─ 按 seq 拼接转写稿
            └─ POST /api/ai/minutes（title/参与人/转写稿）→ Markdown 纪要
                 └─ call_recording.status: UPLOADED → TRANSCRIBING → READY / FAILED
```

客户端在通话详情里轮询 `GET /api/media/calls/{id}/recording`，转写中每 4 秒一次，最多约 1 分钟。

## 2. 为什么录音必须在客户端做

现有通话是 WebRTC 网状（mesh）点对点，服务器只转发 SDP/ICE 信令，**从不接触媒体流**——这是 `docs/实时通话设计.md` 里明确的隐私承诺。

要改成服务端录音，等于引入 SFU（mediasoup/LiveKit 之类）把媒体汇到服务器，架构、带宽、运维成本都会跳一个量级。本期不做。

客户端录音的代价是：只有录音的那个人手里有音频。因此：

- 录音发起人全程负责录制，别人不需要（也不应该）重复录；
- 录音状态由服务端广播，房间里所有人都在界面上看到「● 录音中（由 XX 录制）」；
- 提交时要求 `consent=true`，且只有**接听过**这通电话的成员能提交。

## 3. 为什么分段

| 限制 | 数值 | 影响 |
| --- | --- | --- |
| qwen3-asr-flash 单次输入 | 10MB、约 5 分钟 | 长通话必须切段 |
| base64 编码膨胀 | ×4/3 | 实际按 6MB 原始音频控制 |
| webm 容器 | 只有第一段带 EBML 头 | 不能「切片」，只能「分段重开」 |

所以 `CallRecorder` 每 180 秒主动 `stop()` 当前 recorder 再新建一个，得到若干个**可独立解码**的文件。单段失败不会污染其他段，重试也只重新转写。

## 4. 数据模型（family_media）

```sql
call_session.recording   BOOLEAN  -- 是否正在录音，所有人可见
call_session.recorded_by BIGINT   -- 谁开的录音，停止后置空

call_recording(
  id, call_id UNIQUE, household_id, title, status,
  duration_ms, recorded_by, consent_confirmed,
  transcript TEXT, minutes TEXT, error, created_at, updated_at)

call_recording_segment(
  id, recording_id, seq UNIQUE(recording_id, seq), file_id, duration_ms, transcript TEXT)
```

音频本体不进数据库，只在文件服务里存一份私有文件；`call_recording` 只持有 `file_id`。

## 5. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/media/calls/{callId}/recording` | 提交录音（`consent`、`durationMs`、`segments[{fileId,durationMs}]`） |
| GET | `/api/media/calls/{callId}/recording` | 某通电话的纪要；没录音返回 `null` |
| GET | `/api/media/recordings?page&size` | 家庭纪要列表（不含正文） |
| GET | `/api/media/recordings/{id}` | 详情（含转写稿与纪要全文） |
| POST | `/api/media/recordings/{id}/retry` | 失败重试，录音文件不用重传 |
| POST | `/api/ai/transcribe` | 内部：单段转写（`fileId`） |
| POST | `/api/ai/minutes` | 内部：转写稿 → Markdown 纪要 |

信令新增 `call.record`（`{callId, on}`），服务端写库后广播 `{call, recording, by}`。

## 6. 权限

- 提交：必须接听过该通话（`joined_at` 非空），且 `consent=true`；
- 查看：参与者或管理员；跨家庭一律 404；
- 停止录音：录音发起人或管理员；
- AI 服务：要求登录态，媒体服务把提交者的 `Authorization` 原样转发，转写下载音频也受同一权限约束——后台任务不是越权通道。

## 7. 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `FAMILY_AI_API_KEY` | 空 | 与对话共用；为空时 `/api/ai/transcribe` 返回 503 |
| `FAMILY_AI_BASE_URL` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | OpenAI 兼容端点 |
| `FAMILY_AI_ASR_MODEL` | `qwen3-asr-flash` | 必须支持 `input_audio`（base64） |
| `FAMILY_AI_MODEL` | `qwen-plus` | 生成纪要用的对话模型 |
| `FAMILY_MEDIA_AI_URL` | `http://127.0.0.1:8091` | 媒体服务访问 AI 服务的地址 |

不需要把音频上传到任何第三方存储：转写走 base64，音频只在本服务内存里过一遍。

## 8. 失败与重试

| 现象 | 表现 | 处理 |
| --- | --- | --- |
| AI 未配置 | 提交后 `FAILED`，error 提示未配置 | 管理端填 key 后点「重新生成」 |
| 单段转写失败 | 整体 `FAILED`，已成功的段落已落库 | 重试只重跑整通（幂等覆盖 transcript） |
| 全程静音 | `FAILED`：没有识别到语音内容 | 提示用户检查麦克风 |
| 进程重启 | 停留在 `TRANSCRIBING` | 用户可点重试；不做自动续跑，避免重复计费 |

## 9. 已知限制

1. **没有说话人分离**：混音成单轨后，转写稿没有「谁说的」。纪要里的负责人只能依据对话内容推断，模型被要求「不确定就写待确认」。
   - 改进方向：本地麦克风与远端各录一轨，分别转写后按时间标注「我 / 家人」；ASR 调用次数翻倍。
2. **回声与音量**：混音里同时有本地麦克风与远端流。麦克风沿用通话时已开启的 `echoCancellation`，
   浏览器 AEC 会压制扬声器回放；但外放音量很大、或设备 AEC 效果差时，转写稿里可能出现重复句。
   戴耳机可完全避免。远端音量偏小也会导致漏词。
3. **iOS 容器为 m4a**：`MediaRecorder` 在 Safari 只给 mp4，服务端按文件头嗅探 MIME，不依赖扩展名。
4. **不落公网**：长音频（>5 分钟）无法单次转写，只能靠客户端分段；如果将来要支持超长单段，需要引入对象存储 + DashScope 异步任务。
5. 录音只在**开启录音的那台设备**上；那台设备中途退出，之后的内容不会被录到（其余参与者界面仍显示录音中，直到服务端会话结束）。

## 10. 本地验证

1. 启动 `family-user-svc`、`family-file-svc`、`family-media-svc`、`family-ai-svc` 与网关；
2. 管理端「AI 设置」填入 DashScope key 并启用；
3. 两端登录同一家庭，发起语音/视频通话，接听后点「通话纪要」→ 确认另一端出现「● 录音中」；
4. 说几句话后挂断，等 10-60 秒，在「通话记录 → 详情 → AI 通话纪要」查看结果；
5. 单元测试：`mvn -o -pl family-ai-svc,family-media-svc test`（24 + 22 项）。
   `CallRecordingFlowTest` 用假的 AI 客户端跑完整编排：分段按 seq 拼接、状态推进到 READY、
   静音与转写异常分别落到 FAILED 并保留可读原因。
