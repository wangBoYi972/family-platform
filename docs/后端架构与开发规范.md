# 后端架构与开发规范

日期：2026-09-27。

## 参考依据

已实际阅读本机 TopCloud 的 UserAddrController、UserAddrService、UserAddrServiceImpl、UserAddrMapper、UserAddrDTO、UserVO 和 UserFeignClient。参考其模块与分层组织，自行实现家庭业务，不复制商城业务、凭据或环境配置。

## 服务与数据归属

| 服务 | 职责 | 独占数据库 |
| --- | --- | --- |
| family-user-svc | 白名单、成员、登录会话 | family_user |
| family-content-svc | 任务、公告、日历、动态、相册 | family_content |
| family-file-svc | 文件元数据、访问权限、内容存储 | family_file |
| family-archive-svc | 档案加密、授权读取、审计 | family_archive |
| family-im-svc | 会话、消息、已读游标 | family_im |
| family-media-svc | 音视频会话控制，开发中 | family_media |

Gateway 是统一入口。生产环境通过 Nacos 注册发现和 OpenFeign 调用；local 配置使用显式回环地址。服务账号只应获授本服务数据库权限。禁止跨库 JOIN、跨服务 Mapper 和业务实现依赖。

## 模块边界

- family-common：统一响应和基础类型，不依赖业务服务。
- family-api：Feign 契约与跨服务 ApiVO，不包含 Mapper、Model 或业务实现。
- family-security：JWT、会话校验、统一异常处理和服务客户端注册。
- family-*-svc：可独立启动部署的业务服务，各自维护 Flyway 迁移。

## 服务内部结构

```text
controller     HTTP 协议、参数校验、统一响应
service        业务接口
service/impl   业务规则、权限和本地事务
mapper         MyBatis-Plus BaseMapper 与自定义查询的方法声明
model          数据库映射实体，不直接返回客户端
dto            请求对象，声明校验规则，不信任客户端家庭或所有者标识
vo             返回对象，仅包含场景需要的字段
converter      显式 Model -> VO 转换
config         本服务配置
security       认证或加密实现
resources/mapper       自定义 SQL 的 MyBatis XML 映射
resources/db/migration  本服务表结构版本
```

Controller 仅依赖 Service 接口，不引用 Mapper、Model 或 ServiceImpl。服务层不得使用 HttpServletRequest；身份上下文通过已校验的 SessionPrincipal 传入。DTO 不继承 Model，VO 不包含数据库密文、内部存储路径、会话撤销状态等字段。独立记录类采用 DTO、VO 后缀。

## 依赖注入约定

自 2026-09-29 起，Spring 组件依赖显式使用 @Autowired。普通业务依赖优先采用字段注入；需要在创建时校验配置、初始化密钥、构建存储客户端或映射表的组件，保留构造器并添加 @Autowired。手工创建的值对象和内部辅助对象保留正常构造器，不将其误写成容器依赖。

~~~java
@Autowired
private TaskService service;
~~~

## 事务与服务调用

所有手写 Mapper SQL 统一放在本服务的 `src/main/resources/mapper/*Mapper.xml` 中。Java Mapper 只保留方法声明、`@Mapper` 和 `@Param`，禁止使用 `@Select`、`@Insert`、`@Update`、`@Delete` 及对应 Provider 注解承载 SQL。XML 的 `namespace` 必须对应 Mapper 接口全限定名，语句 `id` 必须对应接口方法名；服务通过 `mybatis-plus.mapper-locations: classpath*:/mapper/**/*.xml` 加载映射。MyBatis-Plus `BaseMapper` 提供的通用 CRUD 继续由框架生成，无须重复手写 SQL。

事务只覆盖当前服务的本地写入。通过远程成员或文件接口验证的数据，不通过跨库查询获取。更新任务使用状态条件进行并发控制；消息以发送者和客户端请求编号实现幂等；点赞在本服务事务内加锁并去重。Feign 显式传递用户凭据，连接超时 2 秒、读取超时 5 秒；故障不返回伪造业务数据。

## 列表分页约定

自 2026-10-31 起，列表接口统一接受可选的 `page`（从 1 开始）与 `size`，由 `com.familyhome.common.api.PageQuery` 归一化：

- 不传参数时等价于改造前的行为（默认取前 500 条，通话记录 30 条、审计 100 条保持原默认值），老客户端不需要改。
- `size` 上限 500，`page < 1` 按 1 处理，`size < 1` 回落默认值；SQL 片段由整数拼成（`PageQuery#limitClause`），无注入面。
- 服务接口保留旧签名（`default` 方法委托到分页版本），避免测试与内部调用方被迫改动。
- 响应仍是数组，判断「是否还有下一页」用 `返回条数 == size`。需要总数时不得在列表接口里额外加 COUNT，另开接口。

已接入：`/api/tasks`、`/api/{kind}`、`/api/files`、`/api/im/conversations`、`/api/archives`、`/api/archives/{id}/audit`、`/api/media/calls/history`。
`/api/im/conversations/{id}/messages` 走游标而不是页码，规则单独一套：

- `after`：取 id > after 的消息、正序、最多 `limit` 条，用于 4 秒轮询追新。
- `before`：取 id < before 的**最近** `limit` 条、仍按正序返回，用于「查看更早的消息」。
- `after` 与 `before` 都不传：返回**最近** `limit` 条。这一步早先写成「正序 + LIMIT 100」，
  等于只给最早的 100 条——会话超过 100 条后，最新消息永远进不了界面。
- `limit` 默认 100（`ImService.MESSAGE_PAGE`），上限 200。前端用「返回条数 == 100」判断还有更早的。

## 列表筛选下推

分页一旦接上，「在客户端过滤」就变成错误做法：客户端手里只有当前一页，本地过滤会把「符合条件但还没加载」的数据彻底藏起来，用户看到的是「搜不到」。

`/api/tasks` 因此接受两个可选筛选参数，筛选条件在 SQL 里展开：

| 参数 | 含义 |
|---|---|
| `keyword` | 标题或负责人姓名模糊匹配，前后空格忽略 |
| `status` | `TODO` / `IN_PROGRESS` / `COMPLETED` / `OVERDUE`，省略或 `ALL` 表示不筛 |

两条实现约束：

- 关键字条件必须包在 `and(...)` 里。直接 `.like(title).or().like(assigneeName)` 会让「家庭隔离」和「负责人」变成 OR，把别的家庭的任务带出来。
- `OVERDUE` 不是存储状态，而是「未完成 + 截止日已过 + 截止日非空」的派生条件；未知取值抛 400，不静默返回全量——拼错参数却没反应比报错更难查。

已下推的接口与参数：

| 接口 | 筛选参数 | 匹配范围 |
|---|---|---|
| `/api/tasks` | `keyword` / `status` | 标题或负责人；`OVERDUE` 为派生条件 |
| `/api/{kind}`（notices/calendar/dynamics/albums） | `keyword` | 标题或正文 |
| `/api/files` | `keyword` | 文件名或 MIME |
| `/api/archives` | `keyword` / `category` | 标题（正文是密文，不参与检索）；分类精确匹配 |

新增列表接口时按同一约定扩展：筛选参数可选、缺省行为不变、条件与权限条件必须分组（`and(...)`）。

## 内容与文件的关联

`content_file_mapping` 是内容与文件关联的唯一真相（`content_type` 取 `NOTICE/CALENDAR/DYNAMIC/ALBUM`）：

- 写入：`ContentFileMappingService#replace` 先删后插，与业务写入同事务；同时继续回写旧列 `file_ids`，保证灰度期间新旧实例都能读。
- 读取：列表批量查映射表（一次 IN 查询，避免 N+1），映射表没有记录的历史行回退旧列。
- 回填：`ContentFileBackfillRunner` 在启动时幂等补齐「旧列有值、映射表为空」的行；失败只记 WARN，不影响启动。
- 删除内容时同步清理关联，避免孤儿行。
- 删除文件时由 `file.deleted` 事件触发 `detachFile`，映射表与旧列一起摘掉该文件（详见下节）。

## 事件消费

发布侧统一走 Outbox（`OutboxEventStore#append` + `OutboxPublisher`），消费侧按服务各自建队列，绑定键都是 `#`——所以**每个开启消息的服务都会收到全站事件**，消费者必须先按 `eventType` 判类型再处理，不能假设队列里只有自己关心的事件。

| 消费者 | 事件 | 动作 |
|---|---|---|
| `im/messaging/FamilyEventConsumer` | 除 `message.sent` 外的全部 | Redis 去重后广播 `{"type":"refresh"}`，客户端收到重拉当前面板 |
| `content/messaging/FileEventConsumer` | `file.deleted` | 调 `ContentFileMappingService#detachFile` 摘掉内容里对该文件的引用 |

`FileEventConsumer` 没有去重表：删映射按 `file_id`、改写旧列按精确比对，重复消费只是白跑一次。异常直接抛出，交给容器重试（3 次）后进死信队列，不静默丢失。

**`message.sent` 为什么单独一路**：聊天要的是「秒上屏」，不是「收到信号再拉一次」。`ImServiceImpl#send`
在**事务提交后**（`TransactionSynchronization#afterCommit`，提前推会把最终回滚的消息显示给家人）把整条消息
序列化成 `{"type":"message",conversationId,messageId,senderId,clientId,kind,body,createdAt}`，
经 `ImSocket#notifyFamilyEvent` 下发。`FamilyEventConsumer` 因此**跳过**这个事件——再发一次 refresh 只会让
所有人的面板白拉一遍接口，而且新消息根本不需要刷新别的面板。
`message.sent` 仍然写 Outbox，留给其它服务做审计/后续处理。

### 实时刷新通道（`/ws/im`）

广播侧早就存在（上表第一行），缺的是客户端——所以「多设备实时刷新」一直是条断头路。现状：

- `POST /api/im/ws-ticket` 用 JWT 换一次性票据（30 秒、用后即焚），再 `wss://host/ws/im?ticket=…` 握手，
  和通话 `/ws/call` 是同一套票据机制，但两条连接分开：`/ws/im` 只发刷新与消息帧，不承载信令。
- 同家庭的所有在线连接都会收到。两种帧：`{"type":"refresh"}`（不知道具体变了什么，客户端重拉当前面板）
  和 `{"type":"message",...}`（带内容，客户端直接上屏）。
- 多实例部署时帧经 Redis 转发：`family:ws:broadcast` 只带家庭号（收到就刷新），
  `family:ws:event` 带整帧 JSON（`{"householdId":10,"frame":{...}}`）。
  转发解析失败只丢这一帧并打 WARN，不能让监听线程挂掉——那台实例会再也收不到任何广播。
- 握手来源白名单以前硬编码 localhost，上线后浏览器带真实域名会被 403 挡掉且没有任何报错。
  现在由 `family.im.allowed-origins`（`FAMILY_IM_ALLOWED_ORIGINS`）配置，默认仍是 localhost 通配。

## 汇总指标接口

列表分页之后，「一共多少条」不能由前端拿当前页去算，也不能在列表接口里顺手加 COUNT。
需要汇总时另开接口，例如 `GET /api/tasks/stats` 返回 `{total, pending, completed, overdue}`：

- 每次三条 `COUNT(*)`，都带 `household_id` 条件，走索引范围扫描，不把数据捞回内存。
- `overdue` 与列表的 `status=OVERDUE` 共用同一个派生条件（未完成 + 截止日早于今天），
  两处口径写在同一个方法里，避免「列表说 3 条、看板说 5 条」。


## Outbox 事件保留期

`OutboxPublisher` 除发布外，每小时按 `family.messaging.retention-days`（默认 7，可用 `FAMILY_MESSAGING_RETENTION_DAYS` 覆盖）分批删除已发布事件；
同时把「超过保留期仍未发布」的 PENDING 数量打成 WARN——它长期不为 0 说明 broker 或消费端有问题，属于要报警的信号，不是噪音。

## 检查与当前限制

运行 backend/pom.xml 的 Maven test 会执行架构约束检查，阻止手写 JDBC、JPA、注解 SQL、Controller 直接访问 Model/Mapper、控制器事务及业务服务实现依赖。编译、真实数据库行为、接口授权和前端联调分别记录，不能用目录存在替代功能验收。

当前 local 使用独立 H2 数据库验证开发流程；生产 MySQL 与 Nacos 仍需真实部署联调。测试验证码仅允许 local profile，正式短信/微信认证需要接入真实平台。音视频媒体能力和多端发布尚未验收，不能宣称整个项目完成。
